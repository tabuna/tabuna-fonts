# Ретроспектива оптимизации glyphs

Дата: 2026-09-12

Документ фиксирует, почему исправление одного символа занимало часы, и какие правила теперь применяются к каждой следующей итерации. Это рабочая матрица решений, а не описание одной разовой попытки.

## Зафиксированные правила

1. Сначала полный baseline `./scripts/run-highlight-audit.sh --sizes 32,64,128 --analyze --verify-repeat`.
2. Выбор glyph выполняется по крупным связным FN/FP и вкладу в ошибку, а не только по минимальному IoU.
3. Для выбранного glyph формулируется ровно одна гипотеза: конкретный узел, сегмент, соединение или endpoint.
4. Пилот меняет один glyph и одну группу (`bbox`, внешняя геометрия, внутренняя геометрия, соединение, endpoint или толщина).
5. До полного аудита сравниваются `IoU`, `FP`, `FN`, `Dice`, `Recall`, BBox и boundary distance выбранного glyph.
6. Изменение принимается только при строгом росте общего IoU, отсутствии роста FN выбранного glyph, отсутствии новой крупной FP-компоненты и воспроизводимости повторного запуска.
7. После трёх последовательных изменений без содержательного уменьшения крупной FN-компоненты направление считается исчерпанным; после пяти отклонённых гипотез требуется ручная разметка узлов или исходный вектор.
8. Если ошибка boundary-only, геометрию не меняем и фиксируем ограничение растрового сравнения.

## Рабочая последовательность для следующего glyph

```text
baseline → priority ranking → error map/BBox → one hypothesis
→ isolated pilot → full audit ×2 → accept/reject → checkpoint
```

Кандидат для продолжения после текущего baseline выбирается из `geometry-audit.json`. На момент этой ретроспективы крупные геометрические ошибки остаются у `Ж`, `Q`, `Я`, `Ю`, `5`, `Л`, `К`; уже реконструированные `з`, `З`, `3` не возвращаются в перебор без новой связной FN-области.

Для восстановления конструктивной логики эталона добавлен
`scripts/infer-reference-logic.py`. Он сохраняет в
`build/reference-contours/logic.json` оси, топологию, толщину и медальные
landmarks. Эти данные используются как стартовая схема новых Bézier-контуров;
они не выдаются за исходный Apple-вектор.

## Ограничение цели

Эталон не содержит исходных Bézier-контуров Apple. Поэтому задача — восстановить топологию, узлы, кривизну и положение штрихов, а затем приблизить растровый край. Полное пиксельное совпадение может быть недостижимо без исходного вектора и точной версии системного рендерера.

Наблюдение из итерации 037: структурное совпадение количества контуров само по
себе не гарантирует улучшение. Для `Я` двухконтурная модель без правильного
положения чаши ухудшила IoU; в следующих реконструкциях topology должна быть
проверена вместе с BBox, узлами соединения и направленными расстояниями границы.
