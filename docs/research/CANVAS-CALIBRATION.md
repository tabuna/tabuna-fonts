# Зависимость Canvas от предварительного рендера DOM

> Исторический отчёт. Упомянутые HTML-стенды и их вспомогательные скрипты
> удалены из публикуемого набора; они не нужны для сборки или использования шрифта.

Проверено 2026-09-11 в Chromium 152, macOS 26.5.2, devicePixelRatio 2.
Файл шрифта во всех опытах — 0.660, без изменений между запусками.
В 0.680 независимый Worker основного стенда расширен до 35 букв и трёх
весов; смешанный Canvas сохраняет 18 букв Regular. Актуальные
итоги приведены в `REVIEW.md`. Числа ниже сохраняют исходный набор опыта.
WOFF2 SHA-256: `3efaa7cb7c3270b261f196dcda5080dd5d59ef7db984fe1772aa0e5df00a9953`.

## Что воспроизведено

При предварительном измерении DOM текст в Canvas получает другие ширины,
чем при запуске Canvas до DOM. Для нашей I:

| Размер | Canvas после DOM | Canvas до DOM | Worker |
| --- | ---: | ---: | ---: |
| 16 | 3.96875 | 3.96875 | 3.96875 |
| 32 | 7.9375 | 7.59375 | 7.59375 |
| 64 | 15.1875 | 14.59375 | 14.59375 |
| 128 | 29.1875 | 28.75 | 28.75 |

Для системной I на 32 px в основном потоке сохраняется ширина 8.96875,
а в Worker — 7.59375. Поэтому проблема касается также состояния эталона.
Порядок размеров по возрастанию/убыванию не изменил собственные ширины
в режиме Canvas до DOM. Масштабирование контекста не изменило ширины.
Измерение до и после fillText дало одинаковые значения.

Это доказывает зависимость результата от контекста и истории рендера.
Взаимодействие кэшей шрифтов — рабочая гипотеза; конкретный дефект
исходного кода Chromium этим опытом не установлен. Не следует подгонять
метрики файла под один такой порядок операций.

## Независимая проверка

`scripts/canvas-worker.js` загружает те же байты WOFF2 в FontFaceSet
отдельного Worker и сравнивает их с system-ui через OffscreenCanvas.
Размер, вес, начало строки и базовая линия одинаковы. Сдвиг, совмещение
изображений и допуск пиксельной ошибки не применяются. Каждый системный
образец отрисовывается дважды для проверки стабильности.

14 букв × 4 размера (16/32/64/128), Regular:

- точная ширина: 56 из 56;
- точные пиксели и ширина: 25 из 56;
- все 56 записей двух независимых запусков совпали;
- самопроверка системного растра: 0 отличающихся пикселей.

На 16 px полностью совпадает I; на 32/64/128 — I/H/E/F/L/Н/Е/І.
Добавленные P/Р/D/B/В/в имеют точные ширины, но ненулевые ошибки рисунка.
В смешанном режиме остаётся 1 полное совпадение из 56. Этот режим сохранён
как отдельная проверка интеграции: Worker не доказывает его исправления.

Данные: `proofs/web-worker-0.660.json`, `proofs/canvas-context-0.660.json`.
Исходный смешанный отчёт: `proofs/web-layout-0.660.json`.

## Воспроизведение

Основной стенд `web-calibration.html` запускает DOM, смешанный Canvas и
независимый Worker отдельно. Диагностический стенд:

- `canvas-calibration.html` — DOM перед Canvas;
- `canvas-calibration.html?phase=canvas-first` — Canvas до DOM;
- `canvas-calibration.html?phase=canvas-first&order=descending` — обратный порядок.

На странице доступны измерения JSON с хешем фактически загруженного файла.
Исторический опыт выше использовал 0.660; живые страницы загружают текущую
сборку из `dist/`. При повторении нужно сохранять хеш измеренного файла.

## Контекст реализации браузеров

В [разборе Chromium](https://web.dev/blog/more-variable-font-options-in-chromium-83)
описаны исторические различия получения оптических метрик и трекинга
через CoreText, Skia и HarfBuzz. Это объясняет необходимость изоляции
таких измерений, но не является доказательством причины текущего эффекта.
[Обсуждение WHATWG](https://github.com/whatwg/html/issues/3571) рассматривает
управление вариативными шрифтами в Canvas отдельно от CSS DOM.
