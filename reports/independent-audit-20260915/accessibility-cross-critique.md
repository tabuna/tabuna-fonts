# Перекрёстная критика после независимого аудита

Первичный accessibility.md не изменён. Здесь отделены собственное повторное наблюдение от результатов других рецензентов.

**Табличные цифры повышают приоритет исправления шрифта.** Я просмотрел новый `engineering/digit-proof.png` и выборку `digit-collisions.json`: в `tnum` слипание отчётливо видно при wght 900 / opsz 128 / 100px, а также в менее крайнем образце wght 725 / opsz 48 / 100px. В пропорциональном столбце при тех же условиях промежутки сохраняются. Инженер сообщает 217 пересечений залитых контуров из 4800 проверенных пар и 0/4800 для pnum. Число 217 — результат его вычислительной проверки, не моя независимо воспроизведённая статистика. Площадь пересечения в JSON подтверждает, что речь не только о пересечении bounding boxes.

Это настоящий P1 для обещанного применения табличных цифр в ценах, счётчиках и крупных числовых индикаторах. Высокий контраст не восстанавливает промежутки между слившимися знаками. Рекомендацию ограниченного пилота следует сузить: до исправления **не использовать heavy/display tnum в функциональных числовых данных**. Ошибка не даёт основания запрещать все текстовые роли 400/500 или весь диапазон pnum. Точный безопасный порог нельзя выводить из четырёх картинок: например, JSON содержит уже wght 725 / opsz 24 для пары 44.

Приёмка: исправить advance/spacing табличных цифр, сохранив равную ширину; повторить полный инженерный sweep и визуально проверить 00, 44, 48, 66, 99 в реальных ценах, процентах и счётчиках на 1x/2x в обеих темах. Ноль пересечений — необходимая геометрическая проверка; удобный межцифровой просвет требует отдельной визуальной проверки. Не заменять tnum на pnum незаметно там, где пользователю нужна устойчивая разрядная сетка. Если используется временное ограничение веса/opsz, публиковать его только по реально проверенной матрице.

**Новая responsive-фикстура уменьшает неопределённость веб-вёрстки.** Root сообщает 64 условия: ширины 288/520, 16/18px, увеличение CSS-размера до 200%, одновременный WCAG spacing override, светлая/тёмная тема; переполнений и обрезаний нет. Отдельно при viewport 320 + 200% + spacing нет горизонтального overflow. Это положительное подтверждение возможности сделать адаптивное чтение с текущим файлом шрифта и выбранными правилами вёрстки. В итоговом отчёте уже нельзя говорить, что увеличение текста нигде не проверялось.

Однако проверена отдельная фикстура. Результат не закрывает A11Y-02 для тесного живого образца демо и не доказывает отсутствие потерь на основном сайте, в другом приложении, при браузерном text-only zoom, VoiceOver или Native Dynamic Type. CSS-увеличение текста также нужно называть именно так. В A11Y-03 остаётся средний приоритет для интеграции; для проверенного шаблона статус можно заменить с «не проверено» на «проверено в указанной матрице». Автоматические границы/overflow не измеряют комфорт чтения, удачность переносов и лёгкость различения знаков.

**Согласие типографа по 400/500 усиливает ограниченный позитивный вывод.** Независимое положительное впечатление от основных латинских и русских форм согласуется с моими новыми короткими образцами. Это согласие экспертов по форме, а не пользовательское исследование. Утверждение о длительном чтении по-прежнему требует читателей, времени чтения, понимания и утомления. Запрет Thin для малого функционального UI остаётся разумным правилом применения; сама возможность выбрать Thin в гарнитуре не является дефектом файла.

Приоритет действий после сопоставления: (1) исправление и регрессионная проверка tnum; (2) зафиксированные роли UI/body без Thin и без display-настроек для мелкого текста; (3) перенос проверенного поведения масштабирования/интервалов в реальный продукт; (4) тесты смешанных кодов и длительного RU/EN чтения. Сертификации HIG, универсальной доступности или эквивалентности системной гарнитуре эти результаты не дают.

Основания доступности: [Apple Typography](https://developer.apple.com/design/human-interface-guidelines/typography), [WCAG Text Spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html), [WCAG Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html). Конкретная оценка P1 и порядок исправления — выводы рецензента из наблюдаемых числовых образцов, а не специальное правило Apple о Tabuna Sans.
