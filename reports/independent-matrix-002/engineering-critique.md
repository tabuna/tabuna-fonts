Initial engineering and data reports remain unchanged. This phase read both reports and the root timer arbitration image/JSON.

The data review's width-stability claim is correct. Independent rerun shaped four timers (`00:00:00`, `11:11:11`, `88:88:88`, `12:34:56`) at 16 axis locations in both decoded formats: all 32 font/location groups have equal timer widths. At 400/14 all four are 8888 units. Every tabular timer nevertheless selects `colon`, not `colon.case`. These are separate properties: equal numeral advances prevent horizontal movement, while the selected colon outline determines vertical alignment. A constant low colon remains low for every timer value and therefore passes width checks.

ENG-001 stands as P2. At default axes the colon drops by 215 units when tnum is enabled. The supplied arbitration image corroborates the lower alignment at 16px, 32px, and especially 64px bold. This is a within-scope feature interaction involving existing digit alternates and U+003A, not missing coverage. Fix it before giving **unconditional UI timer approval** or promising contextual numeral punctuation in both numeric modes. It is not a blocker for merely functioning, fixed-width timers: conditional deployment could knowingly accept the lower colon. This does not warrant rejecting all UI typography or claiming timers jitter.

Acceptance: in TTF and decoded WOFF2, at weights 100/400/700/900 × opsz 9/14/28/128, shape `12:34`, `00:00`, `99:59`, `00:00:00`, `11:11:11`, `88:88:88`, and `12:34:56` with default, pnum, and tnum features while calt is enabled. Every numeric colon must select `colon.case`; ten tnum advances must remain equal with normal kerning enabled; all four equal-format six-digit timers must retain equal widths at each location. Controls: lowercase `a:b` must retain `colon`, uppercase `A:B` must retain `colon.case`, and calt=0 must suppress the contextual substitution. Inspect actual 12/14/16/32/64px timer renders on the intended platform after fixing. Do not require proportional timer widths to become equal.

DATA-01 is a scoped compatibility limitation, not a font defect requiring expansion. Independently confirmed U+202F/U+2009 and ₹/₩/₴/₸/₿ absent, while NBSP, euro and ruble are present. The locked 189-codepoint scope excludes those missing characters. Revise the recommendation toward documenting the repertoire and testing application fallback/formatting for supported locales. Adding characters is a separate scope decision. Acceptance within current scope: the cmap remains the intended 189 mappings; every required in-scope formatted string shapes without .notdef; out-of-scope locale text has an explicit application fallback or approved formatter policy. Do not insist the current font itself shape out-of-scope U+202F without fallback.
